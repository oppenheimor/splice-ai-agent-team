# Taste — 生成后 UI 审查

本 Skill 用于审查许愿池刚生成的本地页面，不要求 URL，也不生成设计分析报告。目标是在交付前发现并修正有实质影响的 UI 问题。

## 审查流程

1. 用 `read_file` 重新读取目标 HTML，不凭刚才的实现印象做结论。
2. 用一句内部判断概括页面的目的、视觉方向和唯一记忆点；如果无法具体概括，说明设计方向尚未成立。
3. 逐项检查以下内容，并用 HTML 结构、CSS 选择器及具体数值作为证据：
   - 首屏是否能快速说明页面是什么、下一步做什么；
   - 标题、正文、辅助信息和主操作是否有明确层级；
   - 字体、颜色、间距、圆角、边框、阴影是否形成一致规则；
   - 布局密度、留白和对齐是否符合内容，而不是机械套模板；
   - 手机窄屏下是否出现挤压、溢出、过小点击区或关键操作不可见；
   - hover、focus、active 和动效是否有意义，并支持键盘与减少动态效果；
   - 装饰是否服务主题，是否压过内容或降低可读性。
4. 专门排查 AI Slop：无依据的紫色渐变、蓝紫发光、同尺寸圆角卡片墙、过量胶囊标签、每个区块都居中、泛滥的毛玻璃、无意义浮动粒子、模板化 Hero、过多阴影层级，以及任何可原样移植到其他产品的装饰。
5. 最多挑出三个最影响体验的问题。若存在问题，不要调用 `write_file`，而是按许愿池 HTML artifact 协议重新输出修正后的完整 HTML；不要只给建议，也不要为了“更有设计感”重写已经成立的部分。
6. 修改后再次 `read_file` 检查相关结构与数值，确认视觉语言一致且没有引入远程资源。

## 判断标准

- 每个正面判断都必须能回答“具体是哪段结构或哪个数值证明了它”，拒绝只说“现代、简洁、高级、直观、丝滑、精致”。
- 好设计来自有意识的取舍。至少确认一项克制：页面主动没有使用什么常见做法，以及为什么不使用更符合当前内容。
- 如果页面已经成立，不为制造修改痕迹而改动；审查通过即可继续 `validate_html`。
- `validate_html` 工具执行失败时只重试同一路径，禁止把基础设施错误当成设计问题重新生成 HTML。
- 本 Skill 不能替代 `validate_html`。视觉审查完成后仍必须执行结构与自包含校验。
