# 许愿池流式预览交互优化 - 会议纪要

## 会议信息

- 日期：2026-07-16
- 话题：许愿池流式预览交互优化
- 参与者：Human、Agent
- 项目/上下文：`splice-ai-agent-team` 项目的 `wish-creator` 产品
- 会议状态：已达成结论

## 结论摘要

当前 HTML 约需 1 分钟才生成完成，仅有顶栏“创作中”和工具卡状态，右侧预览在 `write_file` 完整参数到达前不会变化。会议决定并已实施许愿池专用 HTML artifact 内容流：增量纳入 EVE 持久化会话事件，前端每 400ms 尝试生成安全快照，服务端在校验前把同一响应的最终累计文本落盘。生成期脚本与交互关闭，修改时保留上一完整版本，完成校验后才切为 LIVE。本期未修改 `node_modules` 或扩展 EVE 通用协议，并保留未来抽取通用能力的边界。

## 议题与目标

### 原始问题

> 现在开始编写 HTML 的时候页面上是没有任何交互效果的，而实际上一个 HTML 可能生成要 1 分钟左右，就导致用户看上去像卡住了。

### 最终目标

实现“边生成、边展示局部预览”，且在未完成 HTML、页面修改、手动停止、生成失败、移动端和断线恢复等情况下给出可预期的交互。

## 决策记录

### 决策 1：采用安全快照式局部预览

- 决定：持续接收 HTML 增量，每约 300–500ms 尝试构建可渲染快照；片段未闭合时保留上一帧。
- 理由：兼顾可见进展与稳定性，避免把半截标签或 CSS 强制塞入 iframe 导致白屏、闪烁或错误执行。
- 约束与前提：生成期间禁用 JavaScript，只允许滚动，不允许点击、输入和拖拽。
- 被否决的方案：每收到几个字符就无条件刷新 iframe；使用虚假百分比进度条代替真实局部预览。
- 影响：需要独立的 artifact 解码、安全快照构建和节流逻辑。

### 决策 2：新版本生成期间保留上一个完整版本

- 决定：修改已有页面时，在新版本首个安全快照出现前继续展示旧页面；完整生成失败或被停止时恢复最后完整版本。
- 理由：避免修改动作让用户暂时失去可用页面。
- 约束与前提：首次生成没有旧版本时，失败后保留最后局部快照，但标记为未完成且禁止交互和发布。
- 被否决的方案：生成开始后立即清空预览；增加新旧双栏对比。
- 影响：预览状态需区分最后完整版本、流式草稿和未完成快照。

### 决策 3：建立许愿池专用 HTML artifact 流

- 决定：让 Agent 以专用 artifact envelope 输出 HTML，借助 `message.appended` 的持久化增量实现预览；完整 artifact 再由服务端落盘并校验。
- 理由：已核实 EVE 0.24.3 的对话协议仅在工具参数完整后投影 `actions.requested`，而 `message.appended` 提供可重放的文本增量。
- 约束与前提：artifact 源码不作为普通聊天文字展示；最终落盘 HTML 必须与完整内容流一致。
- 被否决的方案：修改 `node_modules/eve`、为所有 EVE 产品立即增加通用工具参数增量协议；继续使用完整 `write_file` 参数并只加 loading 动画。
- 影响：本期改动仅局限 `wish-creator`，但 codec、快照生成和状态类型应放在子领域边界，方便未来抽取。

### 决策 4：流式状态必须可恢复

- 决定：artifact 增量进入现有 EVE 持久化会话事件；刷新和断线重连后从事件重建最后安全快照。
- 理由：保持与当前“Agent 在服务端继续，完成后自动恢复”的产品承诺一致。
- 约束与前提：不向数据库写入每一帧 iframe 快照，只保存可重放的源事件。
- 被否决的方案：另开一条不持久化的临时 SSE 连接。
- 影响：客户端 reducer 和会话恢复需要识别 artifact 消息。

### 决策 5：在对话与移动端提供可见但不干扰的进展

- 决定：左侧用一张工具卡展示“准备中 → 正在生成 → 正在检查 → 已完成”，可显示已生成内容量和等待时间，但不显示虚假百分比。手机端在首个安全快照出现时自动切到预览一次，用户手动切回后不再抢占页签。
- 理由：让用户同时看到 Agent 正在工作和页面正在成形，又不被滚动源码淹没。
- 约束与前提：Agent 需要用户确认时保持在对话页签。
- 被否决的方案：默认展示持续滚动的原始 HTML；手机端始终停在对话页签。
- 影响：需要同步工具卡、预览状态和移动页签的单次自动跳转状态。

## 实施结果

### 1. 专用 artifact 内容流与落盘闭环

- 新增 `wish-creator-html-artifact:v1` envelope，由 Agent 在可见文本流中持续输出完整 HTML；聊天区识别后隐藏源码，只投影“生成 HTML”进度卡。
- `message.appended` 持续更新当前 artifact 的累计文本和持久化状态；`validate_html` 在同一模型响应内先将最终累计文本写入 sandbox，再执行结构、自包含和体积校验。
- `message.completed` 钩子保留为兜底落盘路径，覆盖未进入校验工具但消息正常完成的情况。
- 运行时发现 DeepSeek 可能在 marker 前加简短说明，解析器因此调整为允许 marker 出现在文本中间；该兼容行为已加入回归测试。

### 2. 安全快照与交互状态

- 前端以 400ms 节流构建草稿快照，丢弃不稳定尾部、移除脚本并补齐可安全关闭的结构；没有可渲染主体时维持上一帧。
- 新版本首帧出现前保留上一个完整版本；生成中统一使用无脚本 sandbox、CSP `script-src 'none'` 和禁用指针交互的预览文档。
- 完整 artifact 通过 `validate_html` 后切换为 LIVE，恢复内联脚本和页面交互；生成停止或失败时回退到最后完整版本，首次生成则冻结最后安全草稿。
- 手机端首个安全快照自动切换到预览一次；需要用户回答问题时保持对话页。

### 3. 可恢复性与快照体积修正

- EVE 的 `message.appended` 携带累计 `messageSoFar`，若将每个增量原样复制到应用快照，请求体会平方级增长。运行时曾观察到快照 PUT 超过 10MB 并返回 413。
- 应用快照现只保留每个 turn/step 最新的一条 artifact 增量，普通对话事件不变；`streamIndex` 仍保留 EVE 原始游标，因此刷新后既能重建最后局部预览，也不会放大请求体。
- 修正后端到端运行中所有相关快照 PUT 均返回 200，刷新会话后 LIVE 预览可正常重建。

### 4. 验证结果

- 自动化：`pnpm test:wish-creator` 通过 12 项测试，覆盖 envelope、marker 前置说明、路径约束、安全快照、旧版本回退、脚本权限、会话恢复和快照压缩。
- 静态检查：`pnpm typecheck` 与本次涉及文件的 ESLint 均通过。
- 构建：`pnpm build` 通过，包括 EVE production build、Next.js 16.2.6 生产编译、类型检查和 23 个静态页面生成。
- 浏览器：完成首次生成、已有页面修改、生成期旧版保留、LIVE 后脚本交互、页面刷新恢复和手机首帧自动切换验证；最终计数器点击“+1”后数值从 0 变为 1。

## 关键讨论回放

### 1. 从“生成反馈”转向“真实局部预览”

- Human：指出 HTML 生成耗时约 1 分钟，页面缺少交互会被误解为卡死；在 Agent 初步建议阶段式反馈后，明确要求“边生成、边展示局部预览”。
- Agent：最初推荐不确定进度动画，随后根据 Human 的选择调整目标，并将稳定快照、脚本禁用和失败回退作为渐进预览的安全边界。

### 2. 从前端小改转向专用 artifact 协议

- 争议：现有 `write_file` 工具卡已有 spinner，但为什么仍无法预览生成中的 HTML。
- Human 的质疑或补充：坚持要看到真实局部页面，不接受只增加 loading 感知。
- Agent 的回应与修正：检查 `WishCreatorSessionShell`、`WishCreatorMessages`、`WishCreatorPreview`、EVE reducer 与协议定义，确认 `actions.requested` 只在工具输入完整时出现；改为利用可持久化的 `message.appended` 承载专用 artifact 流。
- 关键转折：问题的本质不是预览组件没有 loading，而是前端在内容完整前没有任何 HTML 可用。
- 形成的共识：优先实现 `wish-creator` 专用内容流，日后经过实践验证再抽成通用协议。

### 3. 补齐修改、失败、恢复与移动端边界

- Human：逐项确认保留旧版本、生成期可看不可操作、失败回退、持久化恢复、精简工具卡和手机端首帧自动跳转。
- Agent：将这些行为收敛为一组可验收的状态机，并指出 iframe 刷新会丢失页面内部状态，因此生成期不能允许交互。
