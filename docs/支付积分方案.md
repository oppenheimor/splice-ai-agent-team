# 支付积分方案

## 1. 背景

Agent Team 平台会持续扩展不同类型的 Agent。每个 Agent 的交互流程、工具调用、上下文长度和最终产物复杂度都不同，因此支付方案不能只按“对话次数”计费，也不适合在第一版直接做订阅。

第一版采用单一充值包：

> 69 元购买一组积分，用户可随时查看积分余额，并在执行高消耗任务前看到预计消耗。

本方案的核心目标是：让用户理解简单、让系统成本可控、让后续 Agent 扩展时仍然能调整扣费规则。

## 3. 设计原则

### 3.1 前台简单

用户只需要理解：

- 我有多少积分；
- 这次任务预计消耗多少积分；
- 执行完成后实际扣了多少积分；
- 余额不足时如何充值。

前台不展示 token、模型价格、上下文窗口、工具 schema 等工程细节。

### 3.2 后台精确

系统后台需要记录真实成本因子：

- 输入 token；
- 输出 token；
- 模型档位；
- Agent 类型；
- 任务类型；
- 工具调用次数；
- 联网次数；
- 文件数量和文件大小；
- 上下文长度；
- 是否生成结构化交付物；
- 是否发生多轮 Agent 执行循环。

前台积分是产品语言，后台成本是经营语言，两者之间通过可配置扣费规则映射。

### 3.3 先可控，后优化

第一版不追求精确到每个 token 的实时扣费，而是采用“任务包价 + 超额加扣”的方式。

这样可以避免用户觉得扣费黑箱，同时保留后台基于真实成本调价的空间。

## 4. 定价结论

### 4.1 唯一充值包

| 价格 | 获得积分 | 积分心智 |
|---|---:|---|
| 69 元 | 6900 积分 | 1 积分约等于 0.01 元 |

选择 6900 积分的原因：

- 用户容易理解积分价值；
- 69 元可以覆盖多次完整 Agent 任务；
- 后续可通过调整具体 Agent 扣费，而不是频繁调整充值价格；
- 积分包比订阅更适合当前 Agent 类型仍在探索的阶段。

### 4.2 第一版不做的定价形态

第一版暂不做：

- 月订阅；
- 多档套餐；
- 企业版报价；
- 按 token 明细计费；
- 免费额度自动续期；
- 积分赠送活动体系。

这些可以在真实使用数据稳定后再补充。

## 5. 积分消耗模型

### 5.1 基础任务扣费

| 行为 | 扣积分 | 判断标准 |
|---|---:|---|
| 普通对话 / 追问一轮 | 20 | 无工具调用；不生成正式交付物；主要用于解释、追问、补充信息 |
| Agent 轻量分析 | 80 | 有明确分析任务；不读取文件；不联网；不生成长报告 |
| Agent 深度分析 | 200 | 需要多维度判断、权衡、拆解方案；上下文较长；输出较完整但不是最终报告 |
| 生成完整方案 / 报告 | 600 | 生成可直接交付的结构化产物，如方案、计划、清单、诊断报告 |
| 修改、细化已有方案 | 120 | 基于已有产物做局部调整、补充、重写或扩展 |
| 超长上下文、文件、联网、复杂工具调用 | 额外 100-500 | 触发文件解析、联网搜索、多工具循环或超出上下文阈值 |

### 5.2 Agent 级建议扣费

| Agent | 关键行为 | 建议扣费 |
|---|---|---:|
| 需求诊断 Agent | 完成一轮诊断并生成分析结果 | 800 |
| 需求诊断 Agent | 后续追问、解释、局部细化 | 120-200 |
| 寻宝游戏 Agent | 生成完整执行方案 | 1000 |
| 寻宝游戏 Agent | 调整主题、预算、路线、物品清单 | 120-200 |

说明：

- 需求诊断 Agent 不因进入会话或首条消息固定扣 800 积分，应根据本次用户动作的实际产物和消耗扣费；
- Agent 级扣费可以覆盖多次内部对话和推理，不需要用户理解内部细节；
- 同一个 Agent 内部可以继续按步骤拆账，但前台建议展示任务总价；
- 若未来新增 Agent，只需新增该 Agent 的任务扣费配置。

## 6. 行为衡量标准

### 6.1 普通对话

满足以下条件时，按普通对话扣费：

- 不调用工具；
- 不联网；
- 不读取文件；
- 不生成结构化长文；
- 主要回答用户问题、解释已有内容、做轻量追问；
- 输入上下文不超过 3000 tokens；
- 输出不超过 1000 tokens。

建议扣费：20 积分。

### 6.2 轻量分析

满足以下条件时，按轻量分析扣费：

- 用户要求 Agent 做判断、比较、总结或建议；
- 不需要读取外部资料；
- 不需要生成完整方案；
- 输入上下文不超过 8000 tokens；
- 输出不超过 2000 tokens。

建议扣费：80 积分。

### 6.3 深度分析

满足以下条件时，按深度分析扣费：

- 用户问题需要多维度拆解；
- 需要权衡不同方案；
- 需要结合较长上下文；
- 可能包含多次内部模型调用；
- 输入上下文不超过 20000 tokens；
- 输出不超过 4000 tokens。

建议扣费：200 积分。

### 6.4 完整方案 / 报告

满足以下条件时，按完整方案或报告扣费：

- 输出是可直接交付的结构化产物；
- 包含明确章节、步骤、清单、判断或结论；
- 用户可以把结果用于下一步执行或决策；
- 输入上下文不超过 35000 tokens；
- 输出可明显长于普通分析；
- 可能包含多个 Agent 内部步骤。

建议扣费：600 积分起。

### 6.5 修改 / 细化已有方案

满足以下条件时，按修改或细化扣费：

- 基于同一份已有产物继续工作；
- 只修改局部内容；
- 不重新生成完整方案；
- 不新增大量外部资料；
- 不重新执行完整诊断流程。

建议扣费：120 积分。

如果用户要求“重新来一版完整方案”，应按完整方案扣费，而不是按修改扣费。

### 6.6 额外消耗

额外消耗按以下标准加扣：

| 触发项 | 加扣标准 |
|---|---:|
| 超出基础上下文包 | 每额外 10000 input tokens，加扣 100 |
| 超长输出 | 每额外 2000 output tokens，加扣 80 |
| 普通文件解析 | 每个文件加扣 100 |
| 大文件解析 | 根据文件页数、字符量或解析 token 加扣 200-500 |
| 联网搜索 | 每次搜索加扣 50 |
| 打开并读取网页 | 每页加扣 30 |
| 本地低成本工具调用 | 每次加扣 20 |
| 高成本工具调用 | 每次加扣 100 |
| 多轮 Agent 工具循环 | 每多一轮加扣 100 |

第一版可以先只实现部分额外项：

- 联网搜索；
- 网页读取；
- 文件解析；
- 超长上下文；
- 完整报告生成。

其他工具调用可以先记录成本，不立即对用户展示明细。

## 7. 预估与结算流程

### 7.1 执行前预估

用户点击高消耗动作前，系统展示预计消耗：

> 预计消耗：约 200 积分

如果任务包含额外消耗，展示原因：

> 包含：深度分析、较长上下文

如果用户明确要求生成完整诊断报告，再展示更高预估：

> 预计消耗：约 800 积分  
> 包含：完整诊断报告、联网搜索 2 次、读取网页 3 页

### 7.2 执行中保护

如果执行过程中预计消耗显著超过原预估，应暂停并征求用户确认。

建议阈值：

- 实际预计消耗超过原预估 50%；
- 或额外消耗超过 500 积分；
- 或余额可能不足。

提示文案：

> 这次任务需要继续读取更多资料，预计额外消耗 400 积分。是否继续？

### 7.3 执行后结算

任务完成后展示：

> 本次消耗：760 积分  
> 当前余额：5140 积分

用户可以点击查看简明明细：

| 项目 | 积分 |
|---|---:|
| 完整诊断报告 | 600 |
| 联网搜索 | 100 |
| 网页读取 | 60 |

后台保留更完整的技术明细，但前台默认不展开。

## 8. 余额展示

### 8.1 全局余额入口

建议在应用顶部或用户菜单展示：

> 余额：5420 积分

点击后进入积分页面。

### 8.2 积分页面

积分页面包含：

- 当前余额；
- 充值入口；
- 最近消耗记录；
- 最近充值记录；
- 每次消耗对应的 Agent、任务、时间、积分；
- 退款或失败回滚记录。

### 8.3 Agent 内余额提示

在 Agent 页面中，建议展示轻量余额信息：

> 当前余额 5420 积分，本次预计消耗约 200 积分

余额不足时：

> 当前余额不足，完成本次任务预计需要 200 积分。

提供充值按钮。

## 11. 异常处理

### 11.1 支付成功但积分未到账

处理策略：

- 支付回调必须幂等；
- 支付订单状态和积分流水分开记录；
- 如果支付成功但流水失败，后台任务自动补偿；
- 用户可在订单页看到“处理中”状态。

### 11.2 Agent 执行失败

处理策略：

- 如果任务未产生有效结果，不扣费或自动退回；
- 如果已产生部分结果，可按实际完成度扣费；
- 第一版建议简单处理：任务失败则全额退回本次预扣积分。

### 11.3 用户取消任务

处理策略：

- 如果模型或工具尚未开始执行，不扣费；
- 如果已执行但未生成结果，可扣少量基础成本；
- 第一版建议：取消任务不扣费，后台先记录真实成本，等数据稳定后再细化。

### 11.4 余额不足

处理策略：

- 高消耗任务开始前必须检查余额；
- 余额不足时不能开始任务；
- 普通对话可选择允许消耗到 0 后停止；
- 不允许出现负余额。

## 14. 上线节奏

### 阶段一：只做充值和基础扣费

目标：

- 用户可以充值；
- 用户可以看到余额；
- Agent 任务可以扣积分；
- 任务失败可以退回积分。

### 阶段二：增加预估和明细

目标：

- 执行前展示预计消耗；
- 执行后展示消耗明细；
- 余额不足提前拦截；
- 记录 token 和工具消耗。

### 阶段三：基于真实数据校准扣费

目标：

- 分析每个 Agent 的真实成本；
- 调整任务扣费；
- 判断是否需要新增套餐；
- 判断是否适合引入订阅。

## 15. 待验证问题

上线后需要重点验证：

- 69 元是否是用户愿意无压力尝试的价格；
- 6900 积分是否让用户觉得“够用”；
- 完整报告 600-1000 积分是否合理；
- 用户是否能理解执行前预估和执行后结算；
- 联网、文件、超长上下文的额外扣费是否会降低使用意愿；
- 不同 Agent 的真实毛利差异是否过大；
- 是否需要给新用户少量免费体验积分。

## 16. 当前推荐结论

第一版推荐采用：

> 69 元 = 6900 积分；按 Agent 任务扣费；执行前预估；执行后结算；余额全局可见；后台记录真实成本。

第一版最重要的不是把每个积分算到绝对精确，而是建立一套用户信任的扣费体验和一套后台可校准的成本账本。
