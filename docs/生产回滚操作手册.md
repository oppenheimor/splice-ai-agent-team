# 生产回滚操作手册

本文档适用于 `splice-ai-agent-team` 当前的生产发布架构：GitHub `main` 分支触发火山引擎托管构建，镜像推送到火山引擎容器镜像仓库，流水线通过 SSH 调用服务器上的 `deploy-production.sh` 完成发布。

## 一、回滚原则

1. 生产版本只使用完整 Git commit SHA 标签的不可变镜像，禁止使用 `latest`。
2. 候选容器或数据库 migration 在正式切换前失败时，旧容器仍在服务，不需要回滚。
3. 正式切换后出现应用故障时，优先回滚到上一个已验证成功的镜像。
4. 镜像回滚不会撤销已经执行的数据库 migration。生产 migration 必须遵循 expand/contract，保证新旧两个相邻应用版本都能访问迁移后的数据库。
5. 数据库恢复属于独立的高风险操作。除非已经确认 migration 造成不可逆数据问题并准备停机维护，否则禁止通过恢复旧数据库备份来代替应用镜像回滚。

## 二、什么时候需要回滚

| 现象 | 处理方式 |
| --- | --- |
| 候选容器预热失败 | 不需要回滚；发布脚本尚未替换正式容器。 |
| `prisma migrate deploy` 失败 | 不需要回滚应用；旧容器仍在运行，先修复 migration。 |
| 正式容器切换后无法健康启动 | 回滚到上一个成功镜像。 |
| 正式容器健康，但核心功能出现严重回归 | 回滚到上一个成功镜像。 |
| 数据库已经执行不兼容或破坏性 migration | 先停止继续发布，由负责人评估数据库恢复；不要盲目切换旧镜像。 |

## 三、回滚前检查

登录生产服务器：

```bash
ssh heqi@118.196.86.98
cd /home/deploy/agent-team
```

记录当前正式镜像和容器状态：

```bash
docker inspect --format 'current-image={{.Config.Image}} status={{.State.Status}} health={{if .State.Health}}{{.State.Health.Status}}{{else}}missing{{end}}' agent-team-nextjs
docker logs --tail 200 agent-team-nextjs
```

查看本机保留的应用镜像。发布脚本默认保留当前版本和最近两个历史版本：

```bash
docker image ls splice-ai-cn-shanghai.cr.volces.com/splice-ai/agent-team-nextjs \
  --format 'table {{.Repository}}:{{.Tag}}\t{{.CreatedAt}}\t{{.ID}}'
```

从火山引擎成功发布记录或上面的镜像列表中选择上一个完整 commit SHA 标签。不要使用 `latest`、镜像 ID 或 `<none>` 标签。

```bash
ROLLBACK_IMAGE='splice-ai-cn-shanghai.cr.volces.com/splice-ai/agent-team-nextjs:<上一个成功版本的完整 commit SHA>'
docker image inspect "$ROLLBACK_IMAGE" >/dev/null 2>&1 || docker pull "$ROLLBACK_IMAGE"
```

回滚前必须确认该版本与已经执行的数据库 migration 兼容。如果不能确认，先停止操作并检查两个版本之间的 `prisma/migrations/` 变化。

## 四、执行标准回滚

使用现有生产部署脚本执行回滚，不要直接运行 `docker compose up` 绕过候选容器、migration 和健康检查：

```bash
cd /home/deploy/agent-team
bash ./deploy-production.sh "$ROLLBACK_IMAGE"
```

脚本会按以下顺序执行：

1. 拉取指定的不可变镜像；
2. 启动不挂载生产数据卷的候选容器，完成 Eve 预热和 Next.js 健康检查；
3. 验证 Nginx 配置；
4. 执行 `prisma migrate deploy`，确认没有待执行或失败的 migration；
5. 切换正式容器；
6. 等待正式容器健康；
7. reload Nginx 并验证新 upstream；
8. 保留最近三个可回滚镜像版本。

任何步骤失败后都应先读取脚本输出和容器日志，不要连续反复执行回滚。

## 五、回滚后验证

确认容器使用了目标镜像并且健康：

```bash
docker inspect --format 'image={{.Config.Image}} status={{.State.Status}} health={{if .State.Health}}{{.State.Health.Status}}{{else}}missing{{end}} restarts={{.RestartCount}}' agent-team-nextjs
docker logs --tail 100 agent-team-nextjs
```

确认容器内部两个服务和 Nginx upstream：

```bash
docker exec agent-team-nextjs node -e "Promise.all([fetch('http://127.0.0.1:4274/eve/v1/health'),fetch('http://127.0.0.1:3000/agent-team/',{redirect:'manual'})]).then(([eve,next])=>{console.log({eve:eve.status,next:next.status});process.exit(eve.ok&&next.status<500?0:1)}).catch((error)=>{console.error(error);process.exit(1)})"
docker exec nginx wget -q -O /dev/null -T 10 http://agent-team-nextjs:3000/agent-team/
curl -I --max-time 10 https://splice-ai.cn/agent-team/
```

最后进行一次登录、历史会话打开、Wish Creator 生成与预览的人工冒烟验证，并记录：

- 回滚时间；
- 故障镜像 SHA；
- 回滚目标 SHA；
- 回滚原因；
- 验证结果。

## 六、回滚失败时

1. 不要删除当前镜像、历史镜像或生产数据卷。
2. 收集 `docker logs --tail 300 agent-team-nextjs` 和部署脚本完整输出。
3. 检查 `.env` 是否完整、权限是否为 `600`，以及 `app-network`、Nginx 是否正常。
4. 如果问题来自数据库兼容性，停止应用层反复切换，进入数据库恢复评估。
5. 数据库恢复前必须创建当前数据库备份，并明确恢复点与可接受的数据丢失窗口。

## 七、生产环境变量管理

### 变量来自哪里

生产应用变量的唯一运行时来源是服务器文件：

```text
/home/deploy/agent-team/.env
        ↓ docker-compose.yml 的 env_file
agent-team-nextjs 生产容器
```

`DEEPSEEK_API_KEY`、`DATABASE_URL`、`TAVILY_API_KEY` 不从 GitHub Secrets 注入。火山流水线中的 `SERVER_HOST`、`SERVER_USER`、`SERVER_SSH_KEY` 只负责登录服务器；`SCM_COMMIT_ID` 是火山流水线提供的代码版本变量。

### 修改或新增变量

```bash
ssh heqi@118.196.86.98
cd /home/deploy/agent-team
umask 077
cp .env ".env.backup.$(date +%Y%m%d-%H%M%S)"
nano .env
chmod 600 .env
```

只检查变量名，不要把变量值输出到终端或流水线日志：

```bash
awk -F= '/^[A-Z][A-Z0-9_]*=/{print $1}' .env | sort
```

修改 `.env` 不会自动更新正在运行的容器。使用当前不可变镜像重新走一遍发布门禁，使配置安全生效：

```bash
CURRENT_IMAGE="$(docker inspect --format '{{.Config.Image}}' agent-team-nextjs)"
bash ./deploy-production.sh "$CURRENT_IMAGE"
```

新增代码必需的变量时还需要同步完成三件事：

1. 在仓库 `.env.example` 和开发文档中登记变量名，不写真实值；
2. 在服务器 `.env` 中写入真实值并保持权限 `600`；
3. 如果该变量是启动必需项，在火山流水线的生产预检脚本中增加“非空”校验。

### GitHub Secrets 的角色

旧 GitHub Actions 发布流程已经删除，因此仓库中的旧部署 Secrets 不再是生产配置来源。确认没有其他工作流引用后，可以删除旧的服务器、镜像仓库和应用运行时 Secrets。
