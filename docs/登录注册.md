# 登录注册迭代方案

## 目标

先在 `splice-ai-agent-team` 项目内实现一套可运行的注册/登录小闭环，支持逐步学习和迭代；暂不新开独立认证服务，但代码结构要为未来拆分成统一身份服务留好边界。

核心原则：

- **能跑**：每个阶段都能形成独立闭环，避免一开始陷入完整身份系统的复杂度。
- **能学**：按认证系统的关键概念逐步推进，先理解 session，再理解验证码、密码、风控和 SSO。
- **能替换**：业务页面只调用稳定的 auth facade，未来可以把本地实现替换成远程 identity service。

## 当前结论

第一版不要直接做完整注册/登录系统，也不要马上新开独立服务端项目。

推荐先在当前 Next.js 项目内实现：

- `/login` 登录页
- `/api/auth/*` 认证接口
- `lib/auth/*` 认证核心模块
- middleware 保护 `/agent-team/**`
- 使用 TypeScript 编写认证模块和接口，避免 POC 跑通后再从 JavaScript 迁移

后续如果多个项目都要接入，再把 `lib/auth` 抽成共享包或独立 identity service。

## 长期代码边界

业务代码不要直接操作用户表、验证码表、session 表，而是只调用认证模块暴露的稳定接口：

```ts
auth.getCurrentUser()
auth.requireUser()
auth.loginWithSmsCode()
auth.loginWithPassword()
auth.logout()
```

今天这些函数可以访问当前项目数据库；未来拆出去时，这些函数可以改成 HTTP/RPC client，业务页面不需要大改。

建议目录：

```txt
lib/auth/
  index.ts
  session.ts
  user.ts
  sms-code.ts
  password.ts

app/api/auth/
  send-code/route.ts
  login-sms/route.ts
  login-password/route.ts
  logout/route.ts
  me/route.ts
```

## V0：本地假登录

### 目标

先理解登录态的最小模型：浏览器保存 cookie，服务端通过 cookie 判断当前用户。

### 功能

- 新增 `/login` 页面。
- 输入任意手机号或用户名即可登录。
- 登录后写入 cookie。
- `/api/auth/me` 能返回当前登录用户。
- `/agent-team/**` 未登录时跳转到 `/login`。

### 暂不实现

- 数据库
- 密码
- 验证码
- 短信服务
- 注册流程
- 密码加密

### 学习重点

- cookie 是什么。
- session 和 cookie 的关系。
- middleware 如何保护受限路由。
- 服务端如何识别“当前用户”。

### 验收标准

- 未登录访问 `/agent-team/requirements-diagnosis` 会跳转到 `/login`。
- 登录后可以进入受保护页面。
- 刷新页面后仍然保持登录态。
- 点击退出后再次访问受保护页面会回到 `/login`。

## V1：数据库用户 + session

### 目标

从假登录变成真实用户和真实 session。

### 功能

- 新增 `users` 表。
- 新增 `sessions` 表。
- 登录时创建用户和 session。
- cookie 中只保存 `sessionId`，不直接保存用户信息。
- 服务端通过 `sessionId` 查询当前用户。

### 登录方式

先只支持一种方式：

- 手机号直接登录。
- 手机号不存在时自动创建用户。

### 暂不实现

- 真实验证码
- 真实短信服务
- 账号密码登录
- 多设备管理
- 复杂风控

### 学习重点

- 为什么 cookie 里不应该直接放完整用户信息。
- session 如何过期。
- 退出登录为什么需要让 session 失效。
- 用户表和 session 表的职责区别。

### 验收标准

- 首次手机号登录会创建用户。
- 再次使用同一手机号登录会复用同一个用户。
- 删除或过期 session 后，用户需要重新登录。

## V2：手机验证码登录

### 目标

把手机号登录变成更接近真实产品的验证码登录。

### 功能

- 新增 `verification_codes` 表。
- 新增 `/api/auth/send-code`。
- 新增 `/api/auth/login-sms`。
- 验证码有过期时间。
- 验证码有最大尝试次数。
- 同一手机号发送验证码需要做频率限制。

### 短信服务策略

POC 阶段不要先接真实短信服务。

先定义一个可替换接口：

```ts
sendSmsCode(phone: string, code: string): Promise<void>
```

第一版实现可以只打印到控制台：

```ts
export async function sendSmsCode(phone: string, code: string): Promise<void> {
  console.log(`SMS code for ${phone}: ${code}`)
}
```

以后要接阿里云、腾讯云、Twilio 或其他短信服务时，只替换这个函数。

### 学习重点

- 验证码为什么需要过期。
- 验证码为什么需要尝试次数限制。
- 发送频率限制如何防止接口被刷。
- 登录和注册为什么可以在手机号验证码场景下合并。

### 验收标准

- 用户可以请求验证码。
- 控制台能看到验证码。
- 输入正确验证码后登录成功。
- 验证码过期后无法登录。
- 多次输入错误验证码后验证码失效。
- 短时间内重复发送验证码会被限制。

## V3：账号密码登录

### 目标

补齐账号密码登录能力，让用户可以通过传统账号体系登录。

### 功能

- 新增 `password_credentials` 表。
- 支持设置账号和密码。
- 支持账号密码登录。
- 密码必须 hash 后存储。
- 登录失败需要有基础限制。

### 密码存储要求

即使是 POC，也不要明文保存密码。

推荐使用：

- `bcrypt`
- `argon2`

### 暂不实现

- 忘记密码
- 修改密码
- 邮箱验证
- 第三方登录
- 登录设备管理

### 学习重点

- 明文密码为什么危险。
- password hash 和加密的区别。
- salt 的作用。
- 密码登录失败为什么需要限制次数。
- 手机号身份和账号密码身份如何绑定到同一个用户。

### 验收标准

- 用户可以设置密码。
- 数据库中看不到明文密码。
- 正确账号密码可以登录。
- 错误密码无法登录。
- 同一个用户可以同时拥有手机号验证码登录和账号密码登录两种方式。

## V4：完整认证基础设施

### 目标

从“能登录”升级为“可长期维护、可多项目复用”的认证基础设施。

### 功能

- 退出登录。
- session 续期。
- 多设备登录管理。
- 账号绑定手机号和邮箱。
- 用户状态管理：正常、禁用、注销中。
- 登录审计日志。
- Agent 行为审计日志。
- 登录失败限制。
- 用户后台管理。
- 基础风控策略。

### Agent 平台特别需要关注

Agent Team 平台后续不只是普通 Web 登录，还会涉及：

- 哪个用户发起了任务。
- 哪个 Agent 正在代表该用户执行。
- Agent 访问了哪些用户数据。
- Agent 是否执行了超出用户原始意图的动作。

因此后续应逐步补充：

- 身份传播
- 操作审计
- 最小权限
- Agent 任务级授权
- 高风险操作二次确认

### 学习重点

- session 生命周期管理。
- 用户禁用、注销、封禁的区别。
- 审计日志应该记录什么。
- 普通登录、风控验证、强身份验证的边界。
- 什么时候需要 SSO/OAuth/OIDC。

### 验收标准

- 用户可以查看并退出自己的登录设备。
- 禁用用户无法继续登录。
- 关键登录行为有审计记录。
- Agent 执行动作时可以追踪到发起用户。
- 认证模块可以被第二个项目复用。

## 未来拆分路线

### 阶段 A：当前项目内模块化

先把认证能力写在当前项目中，但收敛到 `lib/auth`。

业务页面只调用 auth facade，不直接访问认证数据表。

### 阶段 B：抽成共享包

当第二个项目也需要注册/登录时，把纯逻辑抽成包：

```txt
packages/auth-core/
```

多个项目共同依赖：

```txt
@your-scope/auth-core
```

### 阶段 C：拆成独立 identity service

当多个项目需要统一登录态、统一账号后台、统一审计或跨域身份时，再新建独立服务：

```txt
identity-service/
  /auth/login/password
  /auth/login/sms
  /auth/logout
  /auth/me
  /auth/sessions
  /oauth/authorize
  /oauth/token
```

### 阶段 D：业务项目只保留 auth client

拆分完成后，每个业务项目只保留很薄的一层：

```txt
lib/auth-client/
  get-current-user.ts
  require-user.ts
  logout.ts
```

这层负责读取 cookie、调用 identity service、把用户信息交给业务页面。

## 推荐第一步

先做 V1 的简化版：

> 手机号 + 固定验证码登录，登录成功后创建用户和 session，保护 `/agent-team/**`。

固定验证码可以先使用 `123456`，等流程跑通后再进入 V2，把验证码落表并加上过期、尝试次数和发送频率限制。

这个版本能覆盖登录系统最核心的四件事：

1. 用户是谁。
2. 怎么证明他登录过。
3. 服务端怎么识别他。
4. 未登录时怎么拦截。

## 暂缓事项

以下能力不要在 POC 第一阶段实现：

- 独立认证服务
- OAuth/OIDC/SSO
- 第三方登录
- 真实短信服务
- 实名认证
- 复杂风控
- 多租户权限系统
- 用户后台管理

这些能力都重要，但不适合在还没有完成登录闭环前引入。
